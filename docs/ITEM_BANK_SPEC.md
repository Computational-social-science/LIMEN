# Phase I Item Bank — Specification (for approval before construction)

**Status: spec only. No items exist yet.** This document defines what the Phase I item bank must be so
that the bank can be built and frozen without further design decisions. It is the root dependency of
the runbook: every later step scores against it.

Governing requirements: protocol §4.3 (stimuli), §4.1 (design), §3.1 (wire format), §12 items 1 and 8.

---

## 1. What each item contains

An item is a **short service / routing request** plus the frozen question set Q₀. Nothing else.

| Field | Content | Frozen when? |
|---|---|---|
| `item_id` | stable string, never reused, never renumbered | at construction |
| `state` | 1–3 sentences of English, the request as a user would type it | at construction |
| `domain` | one of `billing` / `access` / `urgency` / `info` | at construction |
| `intent` | a `choice` question with **2–4 caller-defined options** naming the routing decision, plus per-item `criteria` text | at construction |
| `intent_gold` | the locked correct option name | at construction, **before any model sees the item** |
| `ok` | the frozen `noul` question: *"Is the request clear enough to act on?"* | fixed by protocol §3.1 |
| `escalate` | the frozen `noul` question: *"Should a human handle this?"* | fixed by protocol §3.1 |

**Design constraint.** The `intent` options must be **decidable from the state text alone** by a
careful human reader. An item whose gold is arguable is a measurement of the annotator, not of the
model — such items are rejected at construction, not adjudicated later.

## 2. Structure — what makes the design work

| Requirement | Value | Source |
|---|---|---|
| Item count per condition cell | **≥ 4** (not N=1) | protocol §4.3; the audit skill's single-item rule |
| Every item appears under | λ = 0, lo, mid | within-item design, protocol §4.1 |
| Every (item, λ) appears under | ≥ 1 noise seed; confirmatory uses seeds {0,1,2} | pre-registration item 3 |
| Split | **30% dev / 70% test, by `item_id`** | pre-registration item 8 |
| Split integrity | a given `item_id` is wholly in dev or wholly in test — **never** split across seeds or λ | protocol §12 item 8 |
| Domain balance | ≥ 8 items per domain, evenly spread across dev and test | ensures no domain is a test-set accident |
| Parallelism | all four domains carry the same option-count distribution | so option count is not confounded with domain |

**The item is the unit of inference.** The bank's size is set by the power requirement
(`docs/PHASE_I_PREREGISTRATION.md`, O2), not by convenience. Pilot items used to measure the
discordance rate are **excluded from the confirmatory test set**.

## 3. Gold labels

- Gold is **locked before any model runs on the item**. A model's answer never informs a gold label —
  that would invert the measurement.
- Gold is assigned by at least one human pass; a second pass adjudicates disagreements using the
  codebook below.
- **Inter-annotator agreement is recorded** and reported with the bank. A bank whose agreement is poor
  cannot support a 5-point effect.
- Where a `noul` question is used as a primary endpoint, its gold is likewise locked. (Under
  pre-registration item 9, the primary endpoint question is `intent`; `ok` and `escalate` are reported
  as secondary.)

## 4. Adjudication codebook — how disagreements are settled

Named here because protocol §10 requires construction bias to be mitigated by a codebook, and because
an unwritten codebook becomes a post-hoc rationalisation.

1. **Decide from the state text alone.** Not from what the user probably meant, and never from what the
   model said.
2. **Ambiguity is a rejection, not a tiebreak.** If two options are both defensible, the item is
   discarded rather than assigned a gold.
3. **`escalate` gold follows a stated threshold**, not a feeling: gold is *yes* when acting requires
   information the state does not contain, or when the request touches money movement or account
   access that the state does not authorise. That rule is written before the items are labelled.
4. **Domain label is the request's subject**, not the user's tone. An angry billing request is
   `billing`, not `urgency`. `urgency` is reserved for a stated deadline or an explicit escalation
   request.
5. **Ties in a discarded item are logged.** The rejection rate is reported — a high rejection rate is a
   finding about the domain, and hiding it would flatter the bank.

## 5. What the bank must NOT do

- No item may be drawn from, or paraphrased from, the retired programme's distillation corpus. The
  domain differs and the provenance would be wrong; that corpus is archived with the retired object.
- No item may be generated by the pinned model itself — that would make the model both question-setter
  and answerer.
- No adversarial or jailbreak-style misspellings. Out of scope for Phase I (protocol §4.2).
- No OCR, ASR, or cross-lingual material (protocol §4.2, §12 item 1).

## 6. Deliverables when the bank is built

| Artefact | Purpose |
|---|---|
| `items.jsonl` | one item per line, fields of §1 |
| `split.json` | the frozen dev/test id lists, plus a hash of each side |
| `gold.jsonl` | locked labels with the annotator's pass index |
| `agreement.json` | inter-annotator agreement and the rejection log |
| `BANK_SPEC_FROZEN.md` | the bank's own record: counts per domain, per option-count, per split; the hashes; and any deviation from this spec with its reason |

**Freeze is all-or-nothing.** Once frozen, the bank is never edited to improve a result. A defect found
after freezing is reported, not patched, unless it makes the bank invalid — in which case Phase I is
restarted, and that restart is recorded.

## What needs approval before construction

1. **Domain scope.** The protocol says "short service / routing intents (billing, access, urgency,
   info)". Confirm these four, or substitute.
2. **Option counts.** Proposed: `choice` questions carry **2–4** options, distributed so that chance
   accuracy varies within the bank. Alternative: fix at 3 for uniformity at the cost of a constant
   chance floor. The first is preferred because a constant chance floor makes a pooled accuracy
   number easier to over-read.
3. **Bank size.** Cannot be fixed until the pilot measures the discordance rate (pre-registration O2).
   The spec therefore fixes *structure* now and *size* at the amendment.
4. **Who labels.** Gold requires a human pass. If the labelling is done by an agent rather than by the
   researcher, that must be stated in the bank's record, and the agreement statistic becomes the check
   on it.
